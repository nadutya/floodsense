# Как устроен FloodSense MVP

Этот документ подробно объясняет, что происходит в приложении, как выполняются расчёты, за что отвечает backend, какие технологии используются и где проходят границы демонстрационной модели.

## 1. Что именно демонстрирует приложение

FloodSense моделирует небольшой синтетический фрагмент ливневой сети Oxford. Главный сценарий выглядит так:

1. Пользователь задаёт интенсивность дождя.
2. Python рассчитывает поступление воды в каждый сток.
3. Учитываются площадь водосбора, поверхностный сток, пропускная способность и засорённость.
4. Стоки заполняются и могут переливаться на улицу.
5. Избыточная вода частично передаётся следующему стоку сети.
6. Backend определяет риск и рекомендует, куда отправить бригаду.
7. После очистки Python запускает параллельный сценарий и оценивает предотвращённый объём затопления.

Это объяснимая сценарная модель, а не машинное обучение и не инженерно откалиброванный прогноз для реального Oxford.

## 2. Где находятся данные

Демонстрационная сеть описана в файле:

```text
backend/floodsense/data/oxford_demo.json
```

Для каждого стока там заданы:

- уникальный ID;
- условные координаты;
- площадь эффективного водосбора;
- доступный объём локального хранения воды;
- номинальная пропускная способность;
- начальная засорённость;
- коэффициент поверхностного стока;
- отметка высоты;
- следующий сток сети;
- связанный важный объект.

Все эти значения синтетические. Они согласованы между собой для демонстрации, но не являются измерениями Oxfordshire County Council или Thames Water.

## 3. Основная модель

Расчётное ядро находится в:

```text
backend/floodsense/model.py
```

Модель работает с шагом в одну минуту. Каждый сток представлен как накопительный резервуар — `bucket model`.

### 3.1 Превращение дождя в поверхностный сток

Поступление воды рассчитывается по формуле:

```text
inflow = rainfall × catchment_area × runoff_coefficient / 60000
```

Где:

- `rainfall` — интенсивность дождя в мм/ч;
- `catchment_area` — площадь водосбора в м²;
- `runoff_coefficient` — доля осадков, которая не впитывается, а течёт по поверхности;
- результат — м³ воды за минуту.

Деление на `60000` одновременно переводит миллиметры в метры и часы в минуты.

Например, асфальт имеет высокий коэффициент стока: большая часть воды течёт к решётке. Зелёная поверхность имела бы меньший коэффициент.

### 3.2 Пропускная способность

Номинальная пропускная способность хранится в литрах в секунду. Для минутного шага используется:

```text
effective_capacity = capacity_lps × (1 - blockage) × 0.06
```

Здесь:

- `blockage = 0` означает чистый сток;
- `blockage = 0.8` означает 80% засорения;
- множитель `0.06` переводит литры в секунду в кубические метры в минуту.

Таким образом, один и тот же дождь может быть безопасным для чистого стока и критическим для стока, закрытого листьями.

### 3.3 Накопление и перелив

На каждом шаге модель:

1. Добавляет входящий поверхностный поток.
2. Добавляет воду, пришедшую от вышерасположенных участков.
3. Вычитает объём, который успела принять труба.
4. Сравнивает остаток с локальным объёмом хранения.

Если объём превышает `storage_m3`, возникает перелив.

Избыточная вода делится на две части:

- 62% остаётся на поверхности и формирует локальное затопление;
- 38% передаётся следующему стоку через связь `downstream`.

Это упрощённая маршрутизация воды по сети. Она учитывает расположение через заранее заданную топологию, но не вычисляет настоящий путь по цифровой модели рельефа.

### 3.4 Поверхностная вода

Поверхностная вода хранится отдельно от суммарного исторического перелива.

Это важно, потому что факт старого затопления не должен навсегда оставлять сток красным. Текущий риск зависит от воды, которая находится на улице сейчас, а исторический объём используется для оценки последствий.

Без нового притока поверхностная вода постепенно уменьшается:

```text
surface_water = surface_water × 0.94
```

Это приближённо представляет стекание, распределение воды и работу сети после восстановления пропускной способности.

## 4. Засорение, промывка и бесконечный сценарий

Во время дождя листья и мусор постепенно перемещаются к решёткам. Скорость накопления отличается между стоками и зависит от дождя.

Упрощённо:

```text
blockage += debris_sensitivity × rainfall / 60
```

Если просто увеличивать blockage до 100%, через некоторое время все стоки останутся переполненными навсегда. Поэтому в модели есть периодический эффект сдвига листового мата сильным потоком.

У каждого стока собственный цикл. В момент естественной промывки:

- засорённость частично уменьшается;
- локальный накопительный объём освобождается;
- поверхностная вода уходит;
- затем листья снова начинают накапливаться.

Циклы сдвинуты по времени. Поэтому сеть продолжает изменяться: один сток восстанавливается, другой засоряется, третий приближается к переливу.

Это демонстрационное приближение. В реальном продукте изменение blockage должно подтверждаться камерой, датчиком потока и журналом обслуживания.

## 5. Изменение интенсивности дождя

Backend хранит не одно значение дождя, а расписание:

```json
[
  {"minute": 0, "rainfall_mmh": 20},
  {"minute": 35, "rainfall_mmh": 48},
  {"minute": 80, "rainfall_mmh": 12}
]
```

Изменение в интерфейсе начинает влиять на физическое состояние со следующей модельной минуты. Прошлые значения не переписываются.

Визуальная анимация меняется сразу, но уровень воды, показанный для текущей минуты, остаётся прежним.

Сценарий расширяется блоками по 90 минут. Когда пользователь приближается к концу рассчитанного окна, frontend запрашивает продолжение. Поэтому дождь можно воспроизводить неограниченно долго.

## 6. Время до переполнения

Для каждого стока вычисляется текущая чистая скорость наполнения:

```text
net_rate = inflow - effective_capacity
```

Если `net_rate > 0`, приблизительное время до перелива равно:

```text
minutes_to_overflow = remaining_storage / net_rate
```

Если пропускная способность больше входящего потока, ETA отсутствует: при текущих условиях перелив не ожидается.

Это локальная линейная оценка, основанная на текущей интенсивности. Она не является вероятностным прогнозом погоды.

## 7. Риск

Используются четыре состояния:

- `normal` — устойчивое состояние;
- `watch` — сток заметно заполнен или приближается к пределу;
- `high` — до перелива осталось мало времени;
- `critical` — вода уже на поверхности или до перелива остаются последние минуты.

Красный цвет определяется текущим состоянием, а не тем, переполнялся ли сток когда-либо в прошлом.

## 8. Приоритет и рекомендация

Для каждого стока рассчитывается priority score. В него входят:

- срочность;
- уровень засорения;
- важность связанного объекта.

Клиника и экстренный маршрут имеют больший вес, чем обычный участок улицы.

Рекомендация рассчитывается для каждой модельной минуты. Это важно: кнопка `Send crew` должна соответствовать текущему состоянию, а не финалу заранее рассчитанного окна.

## 9. Очистка стока

Когда пользователь нажимает `Send crew to OX-n`, backend добавляет действие в накопительный журнал:

```json
{"drain_id": "OX-103", "minute": 27}
```

В момент очистки:

- blockage сбрасывается примерно до 8%;
- локальный накопительный объём освобождается;
- текущая поверхностная вода убирается;
- прогноз пересчитывается.

История вмешательств накопительная. Очистка второго стока не отменяет очистку первого.

Со временем очищенный сток может снова засориться. Это необходимо для длительного live-сценария и соответствует тому, что обслуживание не решает проблему навсегда.

## 10. Что означает `−9.59 m³ kept off the street`

После вызова бригады Python рассчитывает два сценария:

### Baseline

Что произошло бы, если выбранный сток не очищать.

### Intervention

Что произойдёт при том же дожде, если очистить выбранный сток сейчас.

В обоих сценариях совпадают:

- история дождя;
- текущее время;
- состояние остальных стоков;
- предыдущие выезды бригад.

Затем сравнивается суммарный объём поверхностного перелива:

```text
prevented_overflow = baseline_overflow - intervention_overflow
```

`−9.59 m³` означает, что в сценарии с очисткой на улице оказалось примерно на 9,59 м³ воды меньше. Это модельная контрфактическая оценка, а не прямое показание датчика.

## 11. Датчики и камеры

В панели отображаются два демонстрационных канала.

### Level sensor

`LVL-103 · RX #28` означает:

- `LVL-103` — ID level-сенсора;
- `RX` — получение пакета;
- `#28` — порядковый номер пакета;
- значение в сантиметрах — оценка уровня воды.

График показывает последние 18 показаний.

### Camera

У каждого стока собственная камера: `CAM-101`, `CAM-102` и так далее.

Камера показывает:

- `Recording` — поток доступен;
- `Restoring connection` — краткий демонстрационный сбой;
- `recognition confidence` — уверенность алгоритма в оценке состояния решётки.

Confidence медленно изменяется из-за условных изменений видимости, дождя и загрязнения. Реального computer vision в этом MVP нет: значения синтетические и формируются Python-моделью.

## 12. Backend

Backend построен на Python и FastAPI.

Основные файлы:

```text
backend/floodsense/model.py
backend/floodsense/api.py
backend/floodsense/data/oxford_demo.json
```

### Почему Python

- подходит для численного моделирования;
- имеет зрелую экосистему гидрологических и GIS-инструментов;
- расчётный модуль легко тестировать отдельно;
- в будущем модель можно заменить на SWMM, NumPy или terrain-based расчёт без переписывания интерфейса.

### Почему FastAPI

- автоматически проверяет входные данные;
- создаёт OpenAPI-документацию;
- хорошо работает с type hints;
- имеет небольшой объём служебного кода;
- подходит для асинхронного API и будущих потоков сенсорных данных.

### Pydantic

Pydantic проверяет тела запросов. Например, отрицательная интенсивность дождя или неизвестный формат вмешательства не должны попасть в расчётную модель.

Ошибка `422 Unprocessable Entity` означает, что запрос не прошёл такую проверку. Ранее API ошибочно ограничивал `cleaning_minute` значением 180; после перехода к бесконечному сценарию этот лимит был удалён.

### API

Используются четыре endpoint:

```text
GET  /api/health
GET  /api/network
POST /api/scenarios/run
POST /api/scenarios/compare
```

`run` рассчитывает сценарий, а `compare` строит baseline и intervention.

## 13. Frontend

Frontend использует:

- React;
- TypeScript;
- Vite;
- SVG;
- Canvas;
- CSS.

### React

React управляет состоянием интерфейса:

- выбранным стоком;
- текущей минутой;
- паузой;
- скоростью воспроизведения;
- результатом API;
- открытием боковой панели.

React не рассчитывает физику воды.

### TypeScript

TypeScript описывает структуру API-ответов и помогает обнаруживать ошибки, когда backend и frontend расходятся по формату данных.

### SVG-карта

Карта реализована как локальный интерактивный SVG. Это делает прототип независимым от WebGL и внешнего tile-сервиса.

SVG отвечает за:

- схему улиц;
- позиции стоков;
- выбор объектов;
- pan и zoom;
- подписи;
- цвет риска.

### Canvas

Canvas используется для декоративной анимации:

- дождевых капель;
- брызг;
- кругов на воде;
- визуального затопления;
- молний и грозовых вспышек.

Canvas не меняет состояние модели. Физический объём воды приходит из Python.

## 14. Что такое Vite

Vite — инструмент разработки и сборки frontend-приложений.

Он выполняет две основные задачи.

### Во время разработки

Команда:

```powershell
npm.cmd run dev
```

запускает локальный сервер. Vite:

- открывает приложение на `localhost:5173`;
- преобразует TypeScript и JSX;
- быстро обновляет страницу после изменения файлов;
- проксирует `/api` на FastAPI по адресу `localhost:8000`.

### Для production

Команда:

```powershell
npm.cmd run build
```

создаёт оптимизированные статические файлы в `frontend/dist`.

Vite не является backend и не выполняет Python. Это development server и bundler для браузерной части.

## 15. Почему расчёты не находятся в JavaScript

Frontend получает уже рассчитанный поминутный timeline. Он выбирает нужный кадр и визуализирует его.

В JavaScript разрешены только интерфейсные действия:

- запуск и пауза времени;
- скорость воспроизведения;
- анимация дождя;
- перемещение карты;
- выбор стока;
- отправка REST-запроса.

Риск, ETA, blockage, приоритет, последствия и эффект очистки приходят из Python.

## 16. Тесты

Тесты находятся в:

```text
backend/tests/test_model.py
```

Они проверяют:

- уникальность ID и корректность связей;
- отсутствие перелива без дождя;
- появление отказа при сильном дожде;
- уменьшение затопления после очистки;
- допустимые границы fill level;
- сохранение истории дождя;
- сохранение нескольких вмешательств;
- повторные несинхронные отказы во время длинного шторма.

Запуск:

```powershell
$env:PYTHONPATH="backend"
py -3.10 -m unittest discover -s backend/tests -v
```

## 17. Ограничения MVP

Текущая модель не учитывает:

- настоящий цифровой рельеф Oxford;
- реальные диаметры и уклоны труб;
- уравнение Мэннинга;
- давление и обратный подпор;
- инфильтрацию, меняющуюся во времени;
- вероятностный weather forecast;
- реальные sensor packets;
- реальный computer vision;
- время поездки бригады;
- неопределённость измерений.

Для следующего этапа наиболее ценно заменить bucket-routing на EPA SWMM или откалиброванную network model, подключить реальный rainfall hyetograph и хотя бы один физический level-сенсор.

## 18. Главное архитектурное правило

Python — единственный источник истины для состояния дренажной сети.

```text
Demo data → Python model → FastAPI → React visualization
```

Frontend может красиво показать дождь, но не может самостоятельно решить, какой сток переполнится, когда это произойдёт и сколько воды предотвратила очистка.
